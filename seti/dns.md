# Подтема 11: DNS (Domain Name System)

---

## Часть 1. Теория

### 1.1. Зачем нужен DNS

Люди плохо запоминают цифры. Компьютеры общаются по IP-адресам (например, `142.250.74.78`). Чтобы не заставлять людей запоминать эти цифры, придумали доменные имена (`google.com`, `github.com`).

**DNS (Domain Name System)** — это распределенная система, которая переводит (резолвит) понятные человеку имена в IP-адреса, понятные компьютерам.

---

### 1.2. Иерархия доменов

Доменное имя читается **справа налево** (от старшего к младшему):
`www.example.com.` (точка в конце — это корень, обычно ее опускают).

1. **Корневые серверы (`.`)** — 13 корневых зон по всему миру. Они знают, где находятся серверы зоны `.com`, `.ru`, `.org`.
2. **TLD (Top-Level Domain, первый уровень)** — зоны `.com`, `.ru`, `.net`, `.io`. Они знают, где находятся серверы `google.com`.
3. **Домены второго уровня** — `google.com`, `github.com`.
4. **Поддомены** — `www.google.com`, `api.github.com`.

---

### 1.3. Типы DNS-серверов

*   **Рекурсивный резолвер (Recursive Resolver)** — тот, к которому вы обращаетесь (обычно это DNS вашего провайдера или `8.8.8.8` от Google). Он делает всю грязную работу: если он не знает ответа, он бегает по иерархии (корень -> TLD -> авторитативные серверы) и возвращает вам готовый IP.
*   **Авторитативный сервер (Authoritative Nameserver)** — сервер, который хранит **реальную** зону домена. Он знает точные IP-адреса. Если вы владеете `example.com`, вы настраиваете именно авторитативный сервер (например, через Cloudflare или Route53).

---

### 1.4. Основные типы DNS-записей

| Тип записи | Расшифровка | Что делает | Пример |
|:---|:---|:---|:---|
| **A** | Address | Указывает на IPv4-адрес | `google.com -> 142.250.74.78` |
| **AAAA** | Quad-A | Указывает на IPv6-адрес | `google.com -> 2a00:1450:4010::64` |
| **CNAME** | Canonical Name | Псевдоним (алиас) для другого домена | `www.example.com -> example.com` |
| **MX** | Mail Exchanger | Указывает почтовый сервер | `example.com -> mail.example.com` |
| **TXT** | Text | Текстовая информация (SPF, DKIM, подтверждение домена) | `v=spf1 include:_spf.google.com ~all` |
| **NS** | Nameserver | Указывает авторитативные серверы домена | `ns1.cloudflare.com` |
| **SOA** | Start of Authority | Основная информация о зоне (админ, TTL) | |

---

### 1.5. Как работает резолвинг (пошагово)

Представьте, что вы впервые ввели `example.com` в браузере:

1. **Кэш браузера:** Браузер проверяет свой кэш. Если пусто — идет в ОС.
2. **Кэш ОС:** Операционная система проверяет свой кэш (и файл `/etc/hosts`). Если пусто — идет к рекурсивному резолверу.
3. **Рекурсивный резолвер (ISP):** Резолвер (например, `8.8.8.8`) проверяет свой кэш. Если пусто:
    *   Спрашивает **Корневой сервер**: "Где находится `example.com`?".
    *   Корневой сервер отвечает: "Я не знаю, но вот тебе адрес серверов зоны `.com`".
    *   Резолвер спрашивает **TLD-сервер (`.com`)**: "Где находится `example.com`?".
    *   TLD-сервер отвечает: "Вот тебе адрес авторитативного сервера для `example.com`".
    *   Резолвер спрашивает **Авторитативный сервер**: "Какой IP у `example.com`?".
    *   Авторитативный сервер отвечает: "IP равен `93.184.216.34`".
4. **Ответ:** Резолвер кэширует этот ответ (на время TTL) и отдает его вашей ОС, а ОС — браузеру.

---

### 1.6. TTL (Time to Live)

У каждой DNS-записи есть параметр TTL (время жизни в секундах). Он говорит резолверам, как долго можно хранить этот ответ в кэше. Если вы меняете IP-адрес сайта, изменения вступят в силу только после истечения TTL на всех резолверах в мире.

---

### 1.7. DNS и DevOps

В DevOps DNS используется постоянно:
*   **Kubernetes:** для связи подов между собой (CoreDNS).
*   **Docker:** контейнеры находят друг друга по именам сервисов.
*   **Балансировка:** DNS может возвращать несколько IP-адресов для распределения нагрузки.

## Часть 2. Команды для работы с DNS в Linux

```bash
dig google.com              # полная информация о домене (A-запись)
dig google.com MX           # почтовые записи
dig google.com +short       # только IP-адрес (кратко)
dig google.com @8.8.8.8     # запросить конкретный DNS-сервер
nslookup google.com         # альтернатива (проще)
host google.com             # краткая информация
cat /etc/resolv.conf        # какие DNS-серверы используются
cat /etc/hosts              # локальные переопределения
```

## Часть 3. 10 вопросов с собеседований

### Вопрос 1. Что такое DNS?

**Ответ:**
DNS (Domain Name System) — это распределенная система, которая переводит доменные имена (например, `google.com`) в IP-адреса (например, `142.250.74.78`), понятные компьютерам.

### Вопрос 2. Какие типы DNS-записей вы знаете?

**Ответ:**
*   **A** — домен на IPv4-адрес.
*   **AAAA** — домен на IPv6-адрес.
*   **CNAME** — псевдоним (алиас) для другого домена.
*   **MX** — почтовый сервер.
*   **TXT** — текстовая информация (SPF, подтверждение домена).
*   **NS** — авторитативные серверы домена.

### Вопрос 3. Как происходит резолвинг (превращение домена в IP)?

**Ответ:**
1. Проверка кэша браузера и ОС.
2. Если нет, запрос идет на рекурсивный резолвер (ISP).
3. Резолвер спрашивает корневой сервер -> TLD-сервер (`.com`) -> авторитативный сервер домена.
4. Получает IP-адрес и возвращает его клиенту, кэшируя на время TTL.

### Вопрос 4. Что такое TTL?

**Ответ:**
TTL (Time to Live) — это время (в секундах), на которое DNS-запись кэшируется резолверами. Если TTL равен 3600 (1 час), то изменения DNS-записи вступят в силу только через час, когда кэш обновится.

### Вопрос 5. В чем разница между рекурсивным и авторитативным DNS-сервером?

**Ответ:**
*   **Рекурсивный** — делает всю работу по поиску IP (бегает по иерархии серверов). Обычно стоит у провайдера или в Google (8.8.8.8).
*   **Авторитативный** — хранит реальную зону домена и знает точные ответы. Именно там вы настраиваете записи A, CNAME.

### Вопрос 6. Что такое CNAME-запись и зачем она нужна?

**Ответ:**
CNAME (Canonical Name) — это псевдоним. Она указывает, что один домен является алиасом для другого. Например, `www.example.com` может быть CNAME для `example.com`. Это удобно, чтобы не дублировать IP-адреса.

### Вопрос 7. Что означает ошибка "DNS_PROBE_FINISHED_NXDOMAIN" в браузере?

**Ответ:**
`NXDOMAIN` (Non-Existent Domain) означает, что такого домена не существует. Браузер отправил запрос, а DNS-сервер ответил: "Я не знаю такого имени". Причины: опечатка в адресе, домен не оплачен или не настроен.

### Вопрос 8. Где в Linux хранится файл для локального переопределения DNS?

**Ответ:**
Файл `/etc/hosts`. Он имеет приоритет над DNS-серверами. Например, добавив туда строку `127.0.0.1 mysite.local`, вы заставите компьютер открывать `mysite.local` по локальному адресу.

### Вопрос 9. Какую команду использовать для проверки DNS-записей в Linux?

**Ответ:**
`dig` (Domain Information Groper) — самый мощный инструмент. Например: `dig google.com A` или `dig google.com MX`. Также можно использовать `nslookup` или `host`.

### Вопрос 10. Как DNS связан с Kubernetes?

**Ответ:**
В Kubernetes есть встроенный DNS-сервер (CoreDNS). Когда вы создаете сервис (Service), Kubernetes автоматически создает для него DNS-запись. Поды могут обращаться к другим подам по имени сервиса (например, `http://my-db-service:5432`), а CoreDNS превратит это в нужный IP.
