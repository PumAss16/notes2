# Подтема 15: Сетевая диагностика (Troubleshooting)

---

## Часть 1. Теория

### 1.1. Логика диагностики (С чего начинать)

Когда сеть не работает, нельзя просто «тыкать» команды наугад. Нужно идти **снизу вверх** по модели OSI (от физики к приложению):
1. **Есть ли IP-адрес?** (Физический/Канальный уровень)
2. **Есть ли связь с роутером (шлюзом)?** (Сетевой уровень — `ping`)
3. **Есть ли связь с внешним миром (интернет)?** (Сетевой уровень — `ping 8.8.8.8`)
4. **Работает ли DNS (превращение домена в IP)?** (Прикладной уровень — `dig` или `ping google.com`)
5. **Открыт ли порт на сервере?** (Транспортный уровень — `telnet`, `nc`, `ss`)
6. **Отвечает ли само приложение (HTTP)?** (Прикладной уровень — `curl`, `tcpdump`)

---

### 1.2. Утилиты для Сетевого уровня (IP, ICMP)

**`ping`** — проверяет базовую доступность узла с помощью ICMP-пакетов (эхо-запрос/эхо-ответ).
*   *Зачем нужен:* Проверить, живой ли сервер, и есть ли сеть.
*   *Пример:* `ping -c 4 8.8.8.8` (отправить 4 пакета). Если пинг есть, а сайт не открывается — проблема выше (в DNS или приложении). Если пинга нет — проблема с сетью/фаерволом.

**`traceroute` (или `mtr`)** — показывает маршрут (через какие роутеры) проходит пакет до цели.
*   *Зачем нужен:* Понять, на каком участке сети (у провайдера, в облаке, у сервера) пакет теряется или сильно тормозит.
*   *Пример:* `traceroute google.com`. Если на 5-м хопе время резко прыгает до 1000мс — там проблема.

---

### 1.3. Утилиты для Прикладного уровня (DNS)

**`dig`** — главный инструмент для проверки DNS.
*   *Зачем нужен:* Узнать, какой IP-адрес возвращает DNS для домена, и проверить конкретные записи (A, MX, TXT).
*   *Пример:* `dig google.com +short` (вернет только IP). `dig @8.8.8.8 example.com` (спросить конкретный DNS-сервер).

**`nslookup`** — более старая и простая альтернатива `dig`.
*   *Пример:* `nslookup google.com`.

---

### 1.4. Утилиты для Транспортного уровня (TCP/UDP, Порты)

**`ss` (Socket Statistics)** — современная замена `netstat`. Показывает открытые порты и активные соединения.
*   *Зачем нужен:* Проверить, слушает ли ваш сервер нужный порт (например, 5000) и кто к нему подключен.
*   *Пример:* `ss -tuln` (показать все слушающие TCP/UDP порты). `ss -tulpn | grep 5000` (узнать, какой процесс держит порт 5000).

**`telnet` или `nc` (netcat)** — проверяют доступность конкретного порта на удаленном сервере.
*   *Зачем нужен:* Если `ping` проходит, но сервер не отвечает — нужно проверить порт. Например, если база данных не подключается (порт 5432), можно проверить: `nc -zv 127.0.0.1 5432`.
*   *Пример:* `telnet google.com 443`.

---

### 1.5. Утилиты для Прикладного уровня (HTTP)

**`curl`** — универсальный инструмент для отправки HTTP-запросов из командной строки.
*   *Зачем нужен:* Проверить, отвечает ли веб-сервер, посмотреть заголовки ответа, коды ошибок.
*   *Пример:* `curl -I https://example.com` (показать только заголовки). `curl -v http://localhost:5000` (подробный вывод, включая TLS Handshake).

---

### 1.6. Утилита для глубокого анализа (Перехват пакетов)

**`tcpdump`** — анализатор трафика (сниффер) командной строки.
*   *Зачем нужен:* Когда нужно увидеть, **что именно** летит по сети. Например, если `curl` висит, а `ping` работает, можно запустить `tcpdump` и увидеть, доходят ли TCP SYN-пакеты до сервера.
*   *Пример:* `sudo tcpdump -i any port 5000 -n` (слушать трафик на порту 5000).

**`wireshark`** — графический аналог `tcpdump` (для локального компьютера).

---

### 1.7. Понимание ошибок подключения

*   **Connection refused (Соединение отклонено)** — сервер доступен, но на запрашиваемом порту никто не слушает (программа не запущена).
*   **Connection timeout (Таймаут)** — пакеты не доходят до сервера. Причины: фаервол (DROP), неправильный IP, проблема с маршрутизацией, или сервер выключен.

## Часть 2. Шпаргалка по командам

```bash
# Сетевой уровень (Связь)
ping -c 4 8.8.8.8               # проверить связь с внешним IP
ping -c 4 google.com            # проверить связь + DNS
traceroute google.com           # показать маршрут (на Linux может требовать установки)
mtr google.com                  # интерактивный traceroute

# DNS
dig google.com                  # полная информация о DNS
dig google.com +short           # только IP
dig @8.8.8.8 google.com         # запросить конкретный DNS-сервер

# Транспортный уровень (Порты)
ss -tuln                        # все слушающие TCP/UDP порты
ss -tulpn                       # + PID программ
ss -tulpn | grep 5000           # кто слушает порт 5000
nc -zv 127.0.0.1 5432           # проверить, открыт ли порт (netcat)
telnet google.com 443           # то же самое (telnet)

# Прикладной уровень (HTTP)
curl -I https://example.com     # только заголовки
curl -v https://example.com     # подробный вывод (включая TLS)
curl -k https://example.com     # игнорировать ошибки сертификата

# Перехват трафика
sudo tcpdump -i any port 5000 -n
sudo tcpdump -i any host 8.8.8.8 -n
```

## Часть 3. 10 вопросов с собеседований

### Вопрос 1. Пользователь пишет: "Сайт не открывается". Как вы будете диагностировать проблему?

**Ответ:**
Идем по уровням OSI снизу вверх:
1. Проверяю IP-адрес (`ip a`) — есть ли он вообще.
2. Проверяю пинг до шлюза и до внешнего IP (`ping 8.8.8.8`) — есть ли интернет.
3. Проверяю DNS (`dig сайт.com`) — превращается ли домен в IP.
4. Проверяю порт (`telnet сайт.com 443` или `nc -zv`) — открыт ли он.
5. Проверяю HTTP-ответ (`curl -I https://сайт.com`) — что отвечает сервер.

### Вопрос 2. Чем отличается ping от telnet (или nc)?

**Ответ:**
*   `ping` работает на Сетевом уровне (ICMP) и проверяет, доступен ли сам хост (компьютер/сервер) в принципе.
*   `telnet`/`nc` работают на Транспортном уровне (TCP/UDP) и проверяют, слушает ли конкретная программа конкретный порт на этом хосте.

### Вопрос 3. Что такое traceroute и зачем он нужен?

**Ответ:**
`traceroute` показывает маршрут, по которому пакеты идут до цели (через какие роутеры). Он нужен для поиска проблем на пути: если на каком-то узле время ответа резко растет или пакеты теряются, значит, проблема у конкретного провайдера или на конкретном участке сети.

### Вопрос 4. Как проверить, какой процесс слушает порт 8080?

**Ответ:**
Командой `ss -tulpn | grep 8080` или `lsof -i :8080`. Они покажут PID и имя программы, которая заняла этот порт.

### Вопрос 5. Что такое tcpdump и когда его использовать?

**Ответ:**
`tcpdump` — это сниффер (анализатор трафика). Его используют для глубокой диагностики: когда непонятно, доходят ли пакеты до сервера, и что в них внутри. Например, `sudo tcpdump -i any port 5000 -n` покажет все пакеты на порту 5000.

### Вопрос 6. Как с помощью curl проверить только заголовки HTTP-ответа?

**Ответ:**
С помощью флага `-I` (или `--head`): `curl -I https://example.com`. Это полезно, чтобы увидеть код ответа (200, 404, 500) и тип контента, не скачивая всю страницу.

### Вопрос 7. Пинг до 8.8.8.8 проходит, а ping google.com — нет. В чем проблема?

**Ответ:**
Проблема на уровне **DNS**. Сеть работает (раз пинг до IP идет), но компьютер не может превратить имя `google.com` в IP-адрес. Нужно проверить настройки DNS (`cat /etc/resolv.conf`) и работу DNS-сервера (например, `dig google.com @8.8.8.8`).

### Вопрос 8. Что означает "Connection refused" (Соединение отклонено)?

**Ответ:**
Это ответ на уровне TCP. Он означает, что сервер доступен, но на запрашиваемом порту **никто не слушает** (программа не запущена или слушает другой порт). В отличие от "Connection timeout", когда пакеты просто теряются (например, из-за фаервола).

### Вопрос 9. Что означает "Connection timeout" (Таймаут соединения)?

**Ответ:**
Это означает, что пакеты не доходят до сервера или ответ не возвращается. Причины: фаервол (DROP), неправильный IP, проблема с маршрутизацией, или сервер выключен.

### Вопрос 10. Как посмотреть, какие DNS-серверы использует ваша система?

**Ответ:**
Командой `cat /etc/resolv.conf`. Строки `nameserver ...` показывают IP-адреса DNS-серверов. Также можно посмотреть `resolvectl status` (в системах с systemd-resolved).
