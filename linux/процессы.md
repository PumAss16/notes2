# Подтема 1: Процессы в Linux

---

## Часть 1. Теория

### 1.1. Что такое процесс

**Программа** — это файл на диске (набор инструкций).

**Процесс** — это запущенная программа. Когда вы запускаете программу, ядро:
1. Выделяет ей память (виртуальное адресное пространство).
2. Присваивает PID.
3. Создаёт структуру в ядре (`task_struct`).
4. Ставит в очередь планировщика CPU.

**Из чего состоит процесс:**

| Компонент | Что это |
|:---|:---|
| Код (text) | Инструкции программы |
| Данные (data) | Глобальные переменные |
| Куча (heap) | Динамическая память (`malloc`) |
| Стек (stack) | Локальные переменные, вызовы функций |
| Файловые дескрипторы | Открытые файлы, сокеты |
| Переменные окружения | `PATH`, `HOME` и т.д. |

**Фраза для собеса:**
> Процесс — это экземпляр программы в памяти. Ядро хранит информацию о нём в структуре `task_struct`. У процесса есть PID, память, стек, открытые файлы и переменные окружения.

---

### 1.2. PID, PPID, PGID, SID

| Понятие | Расшифровка | Что это |
|:---|:---|:---|
| PID | Process ID | Уникальный номер процесса |
| PPID | Parent PID | PID родителя |
| PGID | Process Group ID | Группа процессов (для управления сигналами) |
| SID | Session ID | Сессия (обычно = PID лидера сессии) |

**Важные факты:**
- **PID 1** — это всегда `systemd` (или `init`). Он запускается ядром при загрузке, и все остальные процессы — его потомки.
- **PID 0** — это не процесс, а часть ядра (планировщик). Его нет в `ps aux`.
- **Reparenting** — если родитель умирает раньше ребёнка, ребёнок становится приёмным для `systemd` (PID 1), и его PPID меняется на 1.
- **Диапазон PID** — по умолчанию до 32768 (`/proc/sys/kernel/pid_max`), но можно увеличить до 4 миллионов.

**Что такое группа процессов (PGID)?**
Когда вы запускаете команду в терминале, bash создаёт группу процессов. Это нужно, чтобы можно было послать сигнал всей группе сразу (например, `Ctrl+C` посылает SIGINT всей группе).

**Что такое сессия (SID)?**
Сессия — это набор групп процессов, привязанных к одному терминалу. Когда вы закрываете терминал, все процессы сессии получают SIGHUP.

---

### 1.3. fork(), exec(), wait() — три кита Linux

Это системные вызовы, на которых держится запуск процессов.

**fork() — создание копии процесса**
- Создаёт точную копию текущего процесса.
- Родитель и ребёнок продолжают выполнение с одной и той же точки, но у них разные PID.
- С помощью Copy-on-Write (COW) ядро не копирует память физически, пока один из процессов не начнёт её менять.

**exec() — замена процесса**
- Заменяет текущий процесс новой программой.
- PID остаётся тем же, но код, данные и стек полностью заменяются.

**wait() — ожидание завершения ребёнка**
- Родитель вызывает `wait()`, чтобы дождаться завершения дочернего процесса и забрать его exit-код.
- Если родитель не вызовет `wait()`, ребёнок станет зомби.

**Как bash запускает команды:**
```
1. bash вызывает fork() — создаётся копия bash (дочерний процесс)
2. Дочерний процесс вызывает exec() — заменяется на нужную команду (например, ls)
3. Родительский bash вызывает wait() — ждёт завершения ls
4. ls завершается, bash получает exit-код и продолжает работу
```

**Фраза для собеса:**
> Bash запускает команды через fork+exec. fork создаёт копию процесса, exec заменяет её новой программой, а wait позволяет родителю дождаться завершения и получить exit-код.

---

### 1.4. Состояния процессов (STAT в ps aux)

| Код | Название | Описание |
|:---|:---|:---|
| R | Running / Runnable | Выполняется или готов к выполнению |
| S | Sleeping | Спит, ждёт события (interruptible sleep) |
| D | Uninterruptible Sleep | Ждёт I/O, не реагирует на сигналы |
| Z | Zombie | Мёртв, но запись в таблице осталась |
| T | Stopped | Остановлен (SIGSTOP, Ctrl+Z) |
| I | Idle | Праздный поток ядра |

**Дополнительные флаги в STAT:**
- `<` — высокий приоритет
- `N` — низкий приоритет (nice)
- `s` — лидер сессии
- `l` — многопоточный
- `+` — foreground-процесс

---

### 1.5. Сигналы

| Сигнал | Номер | Что делает |
|:---|:---|:---|
| SIGTERM | 15 | Нормальное завершение (по умолчанию в kill) |
| SIGKILL | 9 | Принудительное убийство (нельзя перехватить) |
| SIGHUP | 1 | Перезапуск / перечитать конфиг |
| SIGINT | 2 | Прерывание (Ctrl+C) |
| SIGQUIT | 3 | Выход с дампом памяти (Ctrl+\) |
| SIGSTOP | 19 | Приостановка (нельзя перехватить) |
| SIGTSTP | 20 | Приостановка (Ctrl+Z) |
| SIGCONT | 18 | Продолжить выполнение |
| SIGUSR1/2 | 10/12 | Пользовательские сигналы |

**Важно:**
- `kill <PID>` по умолчанию отправляет SIGTERM (15).
- Процесс может перехватить SIGTERM и обработать его.
- SIGKILL (9) нельзя перехватить — процесс умирает сразу.
- `Ctrl+C` отправляет SIGINT (2) всей группе процессов.

## Часть 2. Команды с флагами

### 2.1. ps — снимок процессов

```bash
ps aux                    # все процессы всех пользователей
ps -ef                    # альтернативный формат (с PPID)
ps -eo pid,ppid,user,cmd  # свой список колонок
ps -p <PID>               # информация о конкретном процессе
ps -u root                # процессы пользователя root
ps --forest               # дерево процессов
```

**Расшифровка колонок ps aux:**

| Колонка | Что означает |
|:---|:---|
| USER | Владелец процесса |
| PID | ID процесса |
| %CPU | Загрузка CPU |
| %MEM | Загрузка RAM |
| VSZ | Виртуальный размер (КБ) |
| RSS | Реально занятая память (КБ) |
| TTY | Терминал (`?` — нет терминала, демон) |
| STAT | Состояние |
| START | Время запуска |
| TIME | Общее время CPU |
| COMMAND | Команда |

**Флаги aux:**
- `a` — все процессы всех пользователей
- `u` — формат с user-friendly колонками
- `x` — включая процессы без терминала (демоны)

---

### 2.2. top / htop — динамический мониторинг

```bash
top                       # интерактивный мониторинг
top -u root               # только процессы root
top -p 1234,5678          # только указанные PID
htop                      # улучшенная версия (если установлена)
```

**Горячие клавиши в top:**
- `q` — выход
- `k` — убить процесс
- `r` — renice (изменить приоритет)
- `M` — сортировка по памяти
- `P` — сортировка по CPU
- `1` — показать все ядра

**Что важно в top:**
- `load average` — средняя нагрузка за 1, 5, 15 минут
- `us` — время CPU на пользовательские процессы
- `sy` — время CPU на системные вызовы
- `wa` — I/O Wait (CPU ждёт диск)
- `id` — простой CPU

---

### 2.3. pstree — дерево процессов

```bash
pstree                    # дерево процессов
pstree -p                 # с PID
pstree -u                 # с пользователями
pstree -p 1               # дерево от systemd
```

---

### 2.4. pgrep — поиск PID по имени

```bash
pgrep nginx               # все PID процессов nginx
pgrep -a nginx            # с командной строкой
pgrep -u root ssh         # только процессы root с именем ssh
pgrep -l nginx            # с именем процесса
```

---

### 2.5. pidof — PID по имени программы

```bash
pidof nginx               # PID всех процессов nginx
```

---

### 2.6. pkill — убить процесс по имени

```bash
pkill nginx               # убить все процессы nginx (SIGTERM)
pkill -9 nginx            # принудительно
pkill -u user1            # убить все процессы пользователя
pkill -f "python script"  # по полной командной строке
```

---

### 2.7. kill — отправить сигнал по PID

```bash
kill 1234                 # SIGTERM (15)
kill -9 1234              # SIGKILL
kill -HUP 1234            # SIGHUP (перечитать конфиг)
kill -l                   # список всех сигналов
kill %1                   # убить задание №1 (jobs)
```

---

### 2.8. jobs / fg / bg — управление заданиями

```bash
sleep 300 &               # запустить в фоне
jobs                      # посмотреть фоновые задачи
fg %1                     # вернуть задание №1 на передний план
bg %1                     # продолжить задание №1 в фоне
Ctrl+Z                    # приостановить текущий процесс
```

---

### 2.9. nice / renice — приоритеты

```bash
nice -n 10 command        # запустить с низким приоритетом
renice -n 5 -p 1234       # изменить приоритет работающего процесса
```

**Диапазон nice:** от -20 (высший приоритет) до +19 (низший).

## Часть 3. 10 вопросов с собеседований (подробно)

---

### Вопрос 1. Что такое PID и PPID?

**Ответ:**

**PID (Process ID)** — это уникальный номер, который ядро присваивает каждому процессу при его создании. PID позволяет однозначно идентифицировать процесс в системе. Диапазон PID по умолчанию — от 1 до 32768, но его можно расширить до 4 миллионов через `/proc/sys/kernel/pid_max`. Когда процесс завершается, его PID может быть переиспользован для нового процесса (но не сразу, чтобы избежать путаницы).

**PPID (Parent PID)** — это PID родительского процесса, то есть того процесса, который создал данный процесс. Любой процесс в Linux (кроме PID 1) имеет родителя. Если родитель умирает раньше ребёнка, ребёнок становится «сиротой» и его PPID автоматически меняется на 1 (systemd). Этот механизм называется **reparenting**.

**Пример:**
```bash
ps -o pid,ppid,cmd -p $$
#   PID  PPID CMD
#  1234  1200 bash
```
Здесь PID = 1234, PPID = 1200 (родитель — терминал или другой shell).

**Почему это важно для DevOps:**
Понимание PID/PPID нужно для диагностики: если процесс перезапускается, вы смотрите PPID и находите родителя (systemd, cron, скрипт). Также PID используется в systemd-юнитах (`PIDFile=`), в Docker (PID 1 внутри контейнера) и в Kubernetes (процессы в подах).

**Фраза для собеса:**
> PID — уникальный номер процесса. PPID — номер родителя. Если родитель умирает, ребёнок становится приёмным для systemd (PID 1), и его PPID меняется на 1.

---

### Вопрос 2. Что такое PID 1 и почему он особенный?

**Ответ:**

**PID 1** — это первый процесс, который запускает ядро Linux при загрузке системы. В современных системах это **systemd** (в старых — `init`). PID 1 является прародителем всех остальных процессов: любой процесс в системе — прямой или косвенный потомок PID 1.

**Особенности PID 1:**
1. **Не может быть убит** обычными сигналами. Ядро игнорирует SIGKILL и SIGSTOP для PID 1. Если PID 1 умирает — система падает с kernel panic.
2. **Усыновляет сирот.** Если родитель умирает раньше ребёнка, ребёнок становится приёмным для PID 1, и его PPID меняется на 1.
3. **Запускает сервисы.** Systemd читает юнит-файлы и запускает демоны (nginx, sshd, docker и т.д.).
4. **Управляет зависимостями.** Systemd знает, какой сервис должен запуститься после какого.

**Пример:**
```bash
ps -p 1 -o pid,ppid,cmd
#   PID  PPID CMD
#     1     0 /sbin/init splash
```
PPID = 0 означает, что родителя нет — процесс создан ядром.

**Почему это важно для DevOps:**
В Docker контейнере **PID 1** — это ваше приложение. Если оно не обрабатывает сигналы (например, SIGTERM), контейнер не завершится корректно. Поэтому в Dockerfile часто используют `tini` или `dumb-init` как PID 1. В Kubernetes это тоже важно: поды должны корректно обрабатывать SIGTERM.

**Фраза для собеса:**
> PID 1 — это systemd. Он запускается ядром, не может быть убит, усыновляет сирот и управляет сервисами. В контейнерах PID 1 — это само приложение, поэтому нужно обрабатывать сигналы.

### Вопрос 3. Как bash запускает команды?

**Ответ:**

Bash использует три системных вызова: **fork()**, **exec()** и **wait()**.

**Пошагово:**
1. **fork()** — bash создаёт свою точную копию (дочерний процесс). У ребёнка тот же код, но новый PID.
2. **exec()** — дочерний процесс заменяет свой код на код нужной программы (например, `ls`). PID остаётся тем же, но память, стек и данные полностью заменяются.
3. **wait()** — родительский bash ждёт завершения дочернего процесса и забирает его **exit-код** (0 — успех, не 0 — ошибка).

**Схема:**
```
bash (PID 1000)
  │
  ├── fork() → дочерний bash (PID 1001)
  │              │
  │              └── exec("ls") → процесс ls (PID 1001)
  │
  └── wait() → ждёт завершения PID 1001
```

**Почему не просто exec()?**
Если бы bash вызывал `exec()` без `fork()`, он бы **заменил сам себя** на `ls`, и после завершения `ls` терминал бы закрылся. `fork()` позволяет родителю остаться в живых и продолжить работу.

**Copy-on-Write (COW):**
`fork()` не копирует память физически — ядро помечает страницы как «общие» и копирует их только при записи. Это делает `fork()` быстрым.

**Фраза для собеса:**
> Bash запускает команды через fork+exec+wait. fork создаёт копию, exec заменяет её новой программой, wait ждёт завершения и получает exit-код.

### Вопрос 4. Что такое зомби-процесс?

**Ответ:**

**Зомби (Z)** — это процесс, который **завершился**, но его родитель **не вызвал wait()** и не забрал exit-код. Запись о процессе остаётся в таблице процессов (ядро хранит PID, exit-код и статистику), но сам процесс уже не работает.

**Как появляется зомби:**
1. Дочерний процесс завершается.
2. Ядро отправляет родителю сигнал SIGCHLD.
3. Родитель должен вызвать `wait()` или `waitpid()`, чтобы забрать exit-код.
4. Если родитель не вызывает `wait()`, ребёнок остаётся зомби.

**Почему зомби нельзя убить через `kill -9`:**
Зомби — это **уже мёртвый** процесс. Сигналы отправляются **живым** процессам. У зомби нет кода, который мог бы обработать сигнал. `kill -9` просто нечего убивать.

**Как избавиться от зомби:**
1. **Заставить родителя вызвать wait()** — например, перезапустить родительский процесс.
2. **Убить родителя** — тогда зомби станет приёмным для systemd (PID 1), а systemd автоматически вызовет `wait()` и уберёт зомби.
3. **Перезагрузить систему** — крайний случай.

**Пример:**
```bash
ps aux | grep defunct
# user  1234  0.0  0.0  0  0 ?  Z  10:00  0:00 [myapp] <defunct>
```
`<defunct>` — признак зомби.

**Почему это важно для DevOps:**
Зомби не занимают CPU и память, но занимают **слот в таблице процессов**. Если зомби накопится много (например, из-за бага в приложении), может закончиться место для новых PID. В контейнерах это особенно критично: если PID 1 не обрабатывает SIGCHLD, зомби накапливаются.

**Фраза для собеса:**
> Зомби — завершившийся процесс, чей родитель не вызвал wait(). Его нельзя убить через kill -9, потому что он уже мёртв. Нужно убить родителя или перезапустить его.

### Вопрос 5. Что делает kill -9 и чем отличается от kill?

**Ответ:**

**`kill <PID>`** по умолчанию отправляет сигнал **SIGTERM (15)**. Это **запрос на нормальное завершение**: процесс может его перехватить, сохранить данные, закрыть соединения и завершиться корректно. Многие демоны (nginx, postgres) обрабатывают SIGTERM и делают graceful shutdown.

**`kill -9 <PID>`** отправляет сигнал **SIGKILL (9)**. Это **принудительное убийство**: сигнал нельзя перехватить, заблокировать или проигнорировать. Ядро немедленно завершает процесс, не давая ему сохранить данные.

**Разница:**

| Характеристика | SIGTERM (15) | SIGKILL (9) |
|:---|:---|:---|
| Перехват | Да | Нет |
| Обработка | Процесс может сохранить данные | Нет |
| Завершение | Graceful | Мгновенное |
| Использование | По умолчанию | Крайний случай |

**Когда использовать:**
- **SIGTERM** — всегда сначала. Дайте процессу шанс завершиться корректно.
- **SIGKILL** — только если процесс завис и не реагирует на SIGTERM.

**Пример:**
```bash
kill 1234        # SIGTERM — вежливо просим завершиться
sleep 5          # ждём 5 секунд
kill -9 1234     # если не умер — убиваем принудительно
```

**Почему это важно для DevOps:**
В Kubernetes при удалении пода отправляется SIGTERM, затем даётся `terminationGracePeriodSeconds` (по умолчанию 30 секунд), и только потом SIGKILL. Если приложение не обрабатывает SIGTERM — данные могут потеряться.

**Фраза для собеса:**
> kill отправляет SIGTERM (15) — процесс может обработать. kill -9 отправляет SIGKILL (9) — нельзя перехватить, процесс умирает мгновенно. Сначала всегда SIGTERM, SIGKILL — крайний случай.

### Вопрос 6. Как найти все процессы пользователя root?

**Ответ:**

Три способа:

**Способ 1: через ps**
```bash
ps -u root
```
Флаг `-u` фильтрует процессы по пользователю. Показывает все процессы root в стандартном формате.

**Способ 2: через pgrep**
```bash
pgrep -u root -a
```
Флаг `-u` — фильтр по пользователю, `-a` — показать полную командную строку. Выводит только PID и команды.

**Способ 3: через ps + awk**
```bash
ps -eo pid,user,cmd | awk '$2 == "root"'
```
Флаг `-e` — все процессы, `-o` — свой список колонок. `awk` фильтрует по второму столбцу (user = root). Это самый гибкий способ: можно добавить любые колонки.

**Дополнительно:**
```bash
# Посчитать количество процессов root
ps -u root | wc -l

# Найти процессы root с именем nginx
pgrep -u root nginx

# Показать дерево процессов root
pstree -u root
```

**Почему это важно для DevOps:**
Процессы root — это системные демоны и сервисы. Их нужно знать, чтобы понимать, что работает в системе. Но убивать их без понимания опасно — можно сломать систему.

**Фраза для собеса:**
> `ps -u root`, `pgrep -u root -a` или `ps -eo pid,user,cmd | awk '$2 == "root"'`.

### Вопрос 7. Что такое PGID и SID?

**Ответ:**

**PGID (Process Group ID)** — это идентификатор **группы процессов**. Группа объединяет несколько процессов для совместного управления сигналами. Когда вы запускаете команду в терминале, bash создаёт новую группу процессов для этой команды. Лидер группы — процесс, чей PID равен PGID.

**Зачем нужна группа:**
Когда вы нажимаете `Ctrl+C`, терминал отправляет SIGINT **всей группе** процессов, а не только foreground-процессу. Это позволяет прервать, например, пайплайн `cat file | grep error | sort` — сигнал получит каждый процесс в пайпе.

**SID (Session ID)** — это идентификатор **сессии**. Сессия — это набор групп процессов, привязанных к одному терминалу. Лидер сессии — процесс, чей PID равен SID (обычно это ваш shell или терминал). Когда вы закрываете терминал, все процессы сессии получают **SIGHUP** (hangup) и завершаются.

**Иерархия:**
```
Сессия (SID)
  ├── Группа процессов (PGID)
  │     ├── Процесс (PID)
  │     └── Процесс (PID)
  └── Группа процессов (PGID)
        └── Процесс (PID)
```

**Пример:**
```bash
ps -o pid,ppid,pgid,sid,cmd -p $$
#   PID  PPID  PGID   SID CMD
#  1234  1200  1234  1234 bash
```
Здесь bash — лидер и группы, и сессии (PID = PGID = SID = 1234).

**Почему это важно для DevOps:**
Понимание PGID/SID нужно для управления фоновыми процессами, для написания скриптов, которые корректно завершаются, и для работы с `nohup`/`setsid` (чтобы процесс не умер при закрытии терминала).

**Фраза для собеса:**
> PGID — группа процессов для управления сигналами (Ctrl+C посылает всей группе). SID — сессия, привязанная к терминалу. При закрытии терминала все процессы сессии получают SIGHUP.

### Вопрос 8. Почему kill возвращает "Операция не позволена"?

**Ответ:**

**Причина:** обычный пользователь может отправлять сигналы **только своим процессам**. Если процесс принадлежит другому пользователю (например, root), ядро проверяет права и запрещает операцию. Это фундаментальный принцип безопасности Linux: пользователь не может влиять на процессы других пользователей.

**Как проверить владельца:**
```bash
ps -o pid,user,cmd -p 39637
#   PID USER  CMD
# 39637 root  sleep 3600
```
Если USER = root, а вы — обычный пользователь, `kill` вернёт «Операция не позволена».

**Решение:**
```bash
sudo kill 39637
sudo kill -9 39637
sudo pkill sleep
```
`sudo` даёт права root, и вы можете отправить сигнал чужому процессу.

**Но осторожно:**
- Убийство системных процессов может сломать систему.
- Убийство процессов других пользователей может нарушить их работу.
- Сначала выясните, что это за процесс: `ps -o pid,ppid,user,cmd -p <PID>`, `cat /proc/<PID>/cmdline`.

**Другой случай:**
Если процесс **ваш**, но `kill` всё равно возвращает ошибку — возможно:
- Процесс уже завершился (PID не существует).
- Процесс — зомби (нельзя убить).
- Процесс в состоянии D (uninterruptible sleep) — сигнал будет доставлен только после выхода из D.

**Фраза для собеса:**
> Обычный пользователь убивает только свои процессы. Для чужих нужен sudo. Но сначала выясните, что это за процесс — убийство системных процессов опасно.

### Вопрос 9. Процесс перезапускается после kill. Почему?

**Ответ:**

**Причина:** процесс **контролируется родителем**, который перезапускает его при падении. Просто `kill` убивает только сам процесс, но родитель (systemd, cron, скрипт-обёртка) видит, что ребёнок умер, и запускает новый.

**Кто может перезапускать:**

| Контроллер | Как проверить | Как остановить |
|:---|:---|:---|
| **systemd** | `systemctl status <service>` | `sudo systemctl stop <service>` |
| **cron** | `sudo crontab -l`, `sudo cat /etc/crontab` | Удалить задание из crontab |
| **Скрипт-обёртка** | `ps -ef | grep <PID>` — найти родителя | `sudo kill <PPID>` |
| **Docker/K8s** | `docker ps`, `kubectl get pods` | `docker stop`, `kubectl delete pod` |

**Как диагностировать:**
1. Найдите PID процесса: `pgrep sleep`
2. Посмотрите PPID: `ps -o pid,ppid,user,cmd -p <PID>`
3. Проверьте родителя: `ps -p <PPID> -o pid,ppid,user,cmd`
4. Проверьте systemd: `systemctl list-units --type=service | grep -i <имя>`
5. Проверьте cron: `sudo crontab -l`, `sudo cat /etc/crontab`

**Пример из вашей практики:**
Вы нашли `run-cups-browse` (часть CUPS — системы печати). Это systemd-сервис, который перезапускается автоматически. Убивать его не нужно — это часть системы.

**Как остановить навсегда:**
```bash
# Если systemd-сервис
sudo systemctl stop <service>
sudo systemctl disable <service>   # запретить автозапуск

# Если cron
sudo crontab -e   # удалить строку

# Если скрипт-обёртка
sudo kill <PPID>   # убить родителя
```

**Фраза для собеса:**
> Процесс перезапускается, потому что им управляет родитель — systemd, cron или скрипт. Нужно найти родителя по PPID и остановить его, а не сам процесс.

### Вопрос 10. Как посмотреть дерево процессов?

**Ответ:**

**Способ 1: pstree** — самый удобный
```bash
pstree                    # дерево процессов
pstree -p                 # с PID
pstree -u                 # с пользователями
pstree -p 1               # дерево от systemd
pstree -p <PID>           # дерево от конкретного процесса
```
Показывает иерархию: кто кого породил. Например:
```
systemd(1)─┬─sshd(1234)───bash(5678)───pstree(9012)
           ├─nginx(2345)─┬─nginx(2346)
           │             └─nginx(2347)
           └─cron(3456)
```

**Способ 2: ps --forest** — встроено в ps
```bash
ps --forest               # дерево в ps
ps -ef --forest           # с PPID и деревом
ps aux --forest | head -30
```
Рисует дерево символами `\`, `_`, `-`.

**Способ 3: ps -ef + grep** — вручную
```bash
ps -ef | grep <имя>
ps -o pid,ppid,cmd -p <PID>
```
Показывает PPID процесса, по которому можно найти родителя.

**Способ 4: /proc**
```bash
cat /proc/<PID>/status | grep PPid
```
Показывает PPID напрямую из ядра.

**Зачем это нужно:**
- Понять, какой процесс родитель (для диагностики перезапусков).
- Найти всех потомков сервиса.
- Увидеть, что запустил ваш shell.
- Диагностировать зомби (найти родителя, который не вызвал wait()).

**Фраза для собеса:**
> `pstree -p` для дерева с PID, `ps --forest` для дерева в ps, `ps -ef | grep` для поиска родителя вручную. Дерево нужно, чтобы понять, кто кого породил, и найти виновника перезапусков.
