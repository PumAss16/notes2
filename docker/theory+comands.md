# Подтема 16: Docker — Теория, Команды и Архитектура

---

## Часть 1. Теория

### 1.1. Зачем нужен Docker (Контейнеризация vs Виртуализация)

Главная боль разработки — это фраза *"У меня на компьютере работает, а на сервере — нет"*. Причина в том, что на сервере может быть другая версия Python, другие библиотеки или другая операционная система.

**Виртуальная машина (VM)** решает эту проблему, но очень тяжело: она запускает **целую гостевую ОС** (со своим ядром) внутри вашей ОС. Это занимает много оперативной памяти и долго загружается.

**Docker (Контейнеризация)** решает ту же проблему, но легковесно. Контейнер **не имеет своего ядра ОС**. Он использует ядро хоста (вашего Linux). Контейнер — это просто изолированный процесс, которому кажется, что он один в системе. Поэтому контейнеры запускаются за секунды и весят мегабайты.

**За счет каких технологий ядра Linux обеспечивается изоляция:**
1.  **Namespaces** — изолируют процессы, сети, файловые системы (контейнер не видит другие процессы).
2.  **Cgroups (Control Groups)** — ограничивают ресурсы (CPU, RAM, диск), чтобы один контейнер не съел всю память.

---

### 1.2. Архитектура Docker

Docker состоит из трех главных частей:
1.  **Docker Daemon (`dockerd`)** — это главный фоновый процесс (сервер). Он делает всю грязную работу: скачивает образы, создает контейнеры, управляет сетями и дисками.
2.  **Docker Client (`docker`)** — это командная строка (CLI). Когда вы пишете `docker run`, клиент отправляет команду Демону через сокет.
3.  **Docker Registry** — это склад (репозиторий) образов. Самый популярный — Docker Hub. Когда вы пишете `docker pull nginx`, Демон идет в Registry и скачивает образ.

---

### 1.3. Образ (Image) и Контейнер (Container) — в чем разница?

*   **Образ (Image)** — это **неизменяемый шаблон** (слепок файловой системы). Он только для чтения (read-only). Его нельзя изменить. Это как ISO-диск с установщиком Windows.
*   **Контейнер (Container)** — это **запущенный экземпляр** образа. У него есть слой для записи (read-write). Это как установленная Windows на компьютере.

Из одного образа можно запустить 100 контейнеров.

**Жизненный цикл контейнера:**
`created` (создан) -> `running` (работает) -> `paused` (приостановлен) -> `exited` (остановлен).

---

### 1.4. Dockerfile и Слои (Layers)

**Dockerfile** — это текстовый файл с инструкциями, как собрать образ. (Как рецепт пирога).
Каждая инструкция в Dockerfile (`FROM`, `RUN`, `COPY`) создает **новый слой (Layer)** в образе. Слои кэшируются. Если вы поменяете одну строчку в конце Dockerfile, Docker не будет пересобирать весь образ, а возьмет старые слои из кэша и соберет только новый.

---

### 1.5. Основные инструкции Dockerfile

*   **FROM** — с какого базового образа начать (например, `FROM ubuntu:22.04`). Всегда первая инструкция.
*   **RUN** — выполнить команду во время сборки образа. Каждый `RUN` создает новый слой.
*   **COPY** — скопировать файлы с вашего компьютера (из контекста сборки) в образ.
*   **ADD** — то же самое, что `COPY`, но умеет распаковывать локальные tar-архивы и скачивать файлы по URL.
*   **WORKDIR** — задать рабочую директорию внутри контейнера (аналог `cd`).
*   **ENV** — задать переменную окружения.
*   **ARG** — задать переменную, доступную *только во время сборки*.
*   **EXPOSE** — указать, какой порт контейнер будет слушать (это документация, порт реально не открывается).
*   **CMD** — команда по умолчанию, которая запускается при старте контейнера. Ее легко переопределить.
*   **ENTRYPOINT** — команда, которая *всегда* запускается при старте. Ее сложно переопределить.
*   **USER** — от какого пользователя запускать процесс (best practice — не от root).

---

### 1.6. Контекст сборки и .dockerignore

**Контекст сборки** — это папка, которую вы передаете в `docker build` (та самая точка в конце: `docker build .`). Весь этот каталог отправляется демону. Если в папке есть тяжелые файлы (например, папка `node_modules` или `.git`), процесс сборки будет очень медленным.
**Решение:** создать файл `.dockerignore` и перечислить в нем то, что не нужно копировать в контекст (по принципу `.gitignore`).

---

### 1.7. Multi-stage build (Многоэтапная сборка)

Это техника, когда в одном Dockerfile используется несколько инструкций `FROM`.
1.  **Первый этап (builder):** ставим компиляторы, скачиваем зависимости, собираем проект.
2.  **Второй этап:** берем чистый, легкий образ (например, `alpine`) и копируем в него только скомпилированный бинарник из первого этапа (через `COPY --from=builder`).

*Результат:* итоговый образ весит мегабайты, а не гигабайты, и не содержит исходников и компиляторов.

---

### 1.8. Best practices для Dockerfile

1.  **Легковесная база:** используйте `alpine` или `distroless`, если возможно.
2.  **Минимум слоев:** объединяйте команды через `&&` (особенно `apt update && apt install -y`).
3.  **Порядок слоев:** сначала копируйте зависимости (и ставьте их), потом код.
4.  **Без root:** создайте пользователя (`RUN adduser`) и переключитесь на него (`USER myuser`).
5.  **Один процесс на контейнер:** не пытайтесь запустить в одном контейнере и Nginx, и базу данных, и Python.

---

### 1.9. Сети в Docker

*   **bridge** (по умолчанию): создается виртуальный мост (`docker0`). Контейнеры получают IP из подсети `172.17.0.0/16`. Чтобы достучаться до них извне, нужен проброс портов (`-p 8080:80`).
*   **host:** контейнер не изолирован от сети хоста. Если приложение в контейнере слушает 8080, оно займет 8080 на вашем компьютере.
*   **none:** сеть отключена, контейнер ни с кем не общается.
*   **overlay:** позволяет соединить контейнеры, работающие на *разных* физических серверах (используется в Docker Swarm и Kubernetes).
*   **macvlan:** контейнер получает реальный MAC-адрес и выглядит для роутера как отдельное физическое устройство.

## Часть 2. Команды Docker

### 2.1. Сборка и работа с образами
*   **`docker build -t myapp:v1 .`** — собрать образ из Dockerfile в текущей директории. `-t` задает имя и тег.
*   **`docker images`** (или `docker image ls`) — список локальных образов.
*   **`docker pull nginx:latest`** — скачать образ из Registry.
*   **`docker push myuser/myapp:v1`** — отправить образ в Registry.
*   **`docker tag myapp:v1 myuser/myapp:v1`** — дать образу новое имя (тег).
*   **`docker history myapp:v1`** — история слоев образа и их размер.
*   **`docker rmi <image_id>`** — удалить образ.

### 2.2. Запуск и управление контейнерами
*   **`docker run -d --name mycontainer -p 8080:80 nginx`** — запустить контейнер. 
    *   `-d` — в фоне.
    *   `-p 8080:80` — проброс портов (хост:контейнер).
    *   `-e VAR=value` — переменные окружения.
    *   `-it` — интерактивный режим.
    *   `--rm` — удалить после остановки.
*   **`docker ps`** — список запущенных контейнеров.
*   **`docker ps -a`** — список всех контейнеров (включая остановленные).
*   **`docker stop mycontainer`** — остановить контейнер (SIGTERM, затем SIGKILL).
*   **`docker start mycontainer`** — запустить остановленный контейнер.
*   **`docker rm mycontainer`** — удалить контейнер.

### 2.3. Диагностика и отладка
*   **`docker logs mycontainer`** — логи контейнера.
    *   `-f` — в реальном времени.
    *   `--tail 50` — последние 50 строк.
*   **`docker exec -it mycontainer bash`** — зайти внутрь работающего контейнера.
*   **`docker inspect mycontainer`** — полная информация о контейнере (JSON).

### 2.4. Сети
*   **`docker network ls`** — список сетей.
*   **`docker network create mynet`** — создать свою сеть.
*   **`docker network inspect mynet`** — информация о сети.
*   **`docker network connect mynet mycontainer`** — подключить контейнер к сети.

### 2.5. Docker Compose
*   **`docker compose up -d`** — поднять все сервисы из `docker-compose.yml` в фоне.
*   **`docker compose down`** — остановить и удалить всё (контейнеры, сети).
*   **`docker compose ps`** — статус сервисов.
*   **`docker compose logs -f`** — логи всех сервисов.
*   **`docker compose build`** — пересобрать образы.

## Часть 3. 10 вопросов с собеседований

### Вопрос 1. Чем контейнеризация отличается от виртуализации?
**Ответ:**
Виртуализация (VM) запускает полноценную гостевую ОС со своим ядром, что тяжело и долго. Контейнеризация (Docker) использует ядро хоста и изолирует процессы. Контейнеры легче, быстрее запускаются и потребляют меньше ресурсов.

### Вопрос 2. За счет каких технологий ядра Linux обеспечивается изоляция контейнеров?
**Ответ:**
За счет двух технологий:
1.  **Namespaces** — изолируют процессы, сети, файловые системы (контейнер не видит другие процессы).
2.  **Cgroups (Control Groups)** — ограничивают ресурсы (CPU, RAM, диск), чтобы один контейнер не съел всю память.

### Вопрос 3. Чем образ (Image) отличается от контейнера (Container)?
**Ответ:**
Образ — это неизменяемый шаблон (слепок файловой системы). Контейнер — это запущенный экземпляр образа с дополнительным слоем для записи.

### Вопрос 4. Что такое Docker Daemon и Docker Client?
**Ответ:**
Docker Daemon (`dockerd`) — это фоновый процесс, который управляет контейнерами, образами и сетями. Docker Client (`docker`) — это CLI-утилита, которая отправляет команды Демону.

### Вопрос 5. Зачем нужен multi-stage build?
**Ответ:**
Это техника в Dockerfile, когда используются несколько блоков `FROM`. Первый этап (stage) может компилировать код (например, Go или React), а второй этап копирует из него только готовый бинарник или статику. Это позволяет сильно уменьшить итоговый размер образа.

### Вопрос 6. Какие типы сетей в Docker вы знаете?
**Ответ:**
*   **bridge** — по умолчанию, виртуальная сеть на хосте.
*   **host** — контейнер использует сеть хоста напрямую.
*   **none** — без сети.
*   **overlay** — для связи контейнеров на разных хостах (Kubernetes).

### Вопрос 7. В чем разница между CMD и ENTRYPOINT в Dockerfile?
**Ответ:**
*   **ENTRYPOINT** — задает команду, которая всегда выполняется при запуске контейнера. Ее сложно переопределить из командной строки.
*   **CMD** — задает команду или аргументы по умолчанию. Их можно легко переопределить, передав свою команду при `docker run`.

### Вопрос 8. В чем разница между COPY и ADD в Dockerfile?
**Ответ:**
Они похожи (копируют файлы с хоста в образ). Но `ADD` умеет делать две дополнительные вещи: автоматически распаковывать локальные tar-архивы и скачивать файлы по URL. `COPY` просто копирует файлы. Best practice — использовать `COPY` для предсказуемости.

### Вопрос 9. Какие есть best practices для написания Dockerfile?
**Ответ:**
1.  Использовать легковесные базовые образы (например, `alpine` или `distroless`).
2.  Объединять команды `RUN` через `&&` для уменьшения слоев.
3.  Использовать `.dockerignore`, чтобы не копировать лишний мусор в контекст сборки.
4.  Использовать multi-stage сборку.
5.  Запускать контейнер от непривилегированного пользователя (не от root).

### Вопрос 10. Что такое Docker Compose и зачем он нужен?
**Ответ:**
Это инструмент для запуска многоконтейнерных приложений. Вы описываете все сервисы (Flask, PostgreSQL, Nginx) в одном файле `docker-compose.yml`, а затем запускаете их одной командой `docker compose up`. Это избавляет от необходимости вручную создавать сети и запускать каждый контейнер отдельно.
