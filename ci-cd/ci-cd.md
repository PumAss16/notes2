## Часть 1. Теория: Методология CI/CD

### 1.1. Что такое CI/CD и зачем это нужно

CI/CD — это не программа, а **философия** и набор практик, которые позволяют доставлять код до пользователей быстро, часто и без боли.

*   **CI (Continuous Integration — Непрерывная интеграция):**
    *   *Суть:* Разработчики часто (несколько раз в день) сливают свой код в общую ветку (например, `main`). Каждый раз, когда кто-то делает `git push`, запускается автоматическая проверка: код собирается, запускаются тесты (линтеры, юнит-тесты). Если что-то сломалось — команда узнает об этом сразу.
    *   *Цель:* Найти баги на ранней стадии.

*   **CD (Continuous Delivery — Непрерывная доставка):**
    *   *Суть:* После успешного прохождения CI, код автоматически собирается в артефакт (например, Docker-образ) и готов к выкатке на сервер. Но **деплой (выкатка) происходит вручную** (по нажатию кнопки). Это нужно, чтобы бизнес мог решать, когда выпускать новую версию.

*   **CD (Continuous Deployment — Непрерывное развертывание):**
    *   *Суть:* То же самое, но **деплой происходит полностью автоматически**. Если тесты прошли — код сразу летит на продакшн к пользователям. Это высший пилотаж, который используют зрелые компании.

### 1.2. Стратегии ветвления (GitFlow и другие)

Чтобы CI/CD работал, нужно договориться, как работать с ветками.
*   **GitFlow:** Строгая модель. Есть ветки `master` (прод), `develop` (разработка), `feature/*` (фичи), `release/*` (подготовка релиза), `hotfix/*` (срочные баги).
*   **Trunk-Based Development:** Все работают в одной ветке (`main`). Ветки живут очень недолго (часы). Это современный стандарт для CI/CD, так как уменьшает конфликты.

### 1.3. Инструменты

*   **GitLab CI/CD:** Встроен прямо в GitLab. Настройка происходит через один файл `.gitlab-ci.yml` в корне репозитория. Очень простой и популярный.
*   **Jenkins:** Старый, мощный, но сложный. Требует настройки сервера, агентов и написания пайплайнов на Groovy.
*   **GitHub Actions:** Современный стандарт для GitHub. Использует YAML-файлы в папке `.github/workflows/`.

## Часть 2. Углубленный синтаксис `.gitlab-ci.yml`

Файл `.gitlab-ci.yml` — это сердце GitLab CI. Он состоит из нескольких ключевых блоков.

### 2.1. Глобальные ключи

Эти ключи пишутся в самом начале файла и применяются ко всем задачам.

*   **`stages`**: Определяет порядок этапов. Задачи внутри одного этапа выполняются **параллельно**, а этапы идут **последовательно**.
    ```yaml
    stages:
      - build
      - test
      - deploy
    ```
*   **`variables`**: Глобальные переменные, доступные всем задачам.
    ```yaml
    variables:
      DOCKER_IMAGE: "my-app"
    ```
*   **`default`**: Значения по умолчанию для всех задач (например, `image`, `tags`).
    ```yaml
    default:
      image: alpine:latest
    ```
*   **`workflow`**: Управляет тем, **когда** запускается весь пайплайн (например, только для Merge Request или только для ветки `main`).
    ```yaml
    workflow:
      rules:
        - if: $CI_COMMIT_BRANCH == "main"
        - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    ```

### 2.2. Задачи (Jobs)

Каждая задача — это отдельный блок YAML. Вот его ключевые параметры:

*   **`script`**: (Обязательный) Список shell-команд, которые выполняет задача.
*   **`stage`**: К какому этапу относится задача (по умолчанию `test`).
*   **`image`**: В каком Docker-образе выполнять задачу. Это критично для воспроизводимости.
*   **`rules`**: Условия, при которых задача **запускается** или **не запускается**. Это гораздо гибче, чем старый `only/except`.
    ```yaml
    deploy_prod:
      rules:
        - if: $CI_COMMIT_BRANCH == "main"
          when: manual # Запуск только вручную
        - if: $CI_COMMIT_BRANCH != "main"
          when: never # Не запускать в других ветках
    ```
*   **`needs`**: Позволяет задаче начать работу, **не дожидаясь** завершения всего предыдущего этапа, а только конкретных задач. Это превращает последовательный пайплайн в граф зависимостей (DAG) и сильно ускоряет сборку.
    ```yaml
    test_frontend:
      stage: test
      needs: ["build_frontend"] # Ждет только сборку фронтенда, игнорируя сборку бэкенда
      script: npm test
    ```

### 2.3. Передача данных между задачами: Artifacts и Cache

Это то, что часто спрашивают на собеседованиях и без чего не построить реальный пайплайн.

*   **`artifacts`**: Файлы, которые задача **сохраняет** после выполнения, чтобы передать их **следующим** задачам (например, собранный бинарник или Docker-образ). Они хранятся в GitLab.
    ```yaml
    build:
      stage: build
      script: go build -o myapp
      artifacts:
        paths:
          - myapp
        expire_in: 1 week # Хранить неделю
    ```
*   **`cache`**: Файлы (например, папка `node_modules` или `.m2`), которые **кэшируются** между запусками пайплайна, чтобы не скачивать зависимости заново. Это **не** передается между задачами, а ускоряет повторные запуски.
    ```yaml
    test:
      stage: test
      cache:
        key: ${CI_COMMIT_REF_SLUG}
        paths:
          - node_modules/
      script: npm ci && npm test
    ```

### 2.4. Окружения (Environments) и Деплой

Для управления деплоем (dev/staging/prod) используется ключ `environment`. Он позволяет GitLab отслеживать, какая версия кода где развернута, и дает кнопки для отката.

```yaml
deploy_staging:
  stage: deploy
  script: ./deploy.sh staging
  environment:
    name: staging
    url: https://staging.example.com
```

## Часть 3. Практика (Сложное задание из роадмапа)

В вашем роадмапе упомянуты варианты усложнения. Вот как выглядел бы пайплайн для **Варианта 1** (три окружения и передача артефактов) для вашего Python-приложения.

**Задача:** Написать `.gitlab-ci.yml`, который:
1.  Собирает Docker-образ на этапе `build` и сохраняет его как артефакт.
2.  На этапе `test` запускает линтер (`flake8`).
3.  На этапе `deploy` деплоит на `dev` (автоматически при пуше в ветку), на `staging` (автоматически при мерже в `main`), на `prod` (только вручную).

**Решение (абстрактный пример):**

```yaml
stages:
  - build
  - test
  - deploy

variables:
  DOCKER_DRIVER: overlay2

# 1. СБОРКА
build_image:
  stage: build
  image: docker:24.0
  services:
    - docker:24.0-dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker save $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o image.tar
  artifacts:
    paths:
      - image.tar
    expire_in: 1 hour

# 2. ТЕСТИРОВАНИЕ
lint_code:
  stage: test
  image: python:3.11-slim
  script:
    - pip install flake8
    - flake8 app.py

# 3. ДЕПЛОЙ (DEV - авто при пуше в любую ветку)
deploy_dev:
  stage: deploy
  image: docker:24.0
  dependencies:
    - build_image
  script:
    - docker load -i image.tar
    - ssh user@dev-server "docker stop myapp || true && docker rm myapp || true"
    - ssh user@dev-server "docker run -d --name myapp -p 5000:5000 $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  environment:
    name: dev
    url: https://dev.example.com
  rules:
    - if: $CI_COMMIT_BRANCH

# 4. ДЕПЛОЙ (STAGING - авто при мерже в main)
deploy_staging:
  stage: deploy
  image: docker:24.0
  dependencies:
    - build_image
  script:
    - docker load -i image.tar
    - ssh user@staging-server "docker stop myapp || true && docker rm myapp || true"
    - ssh user@staging-server "docker run -d --name myapp -p 5000:5000 $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# 5. ДЕПЛОЙ (PROD - только вручную)
deploy_prod:
  stage: deploy
  image: docker:24.0
  dependencies:
    - build_image
  script:
    - docker load -i image.tar
    - ssh user@prod-server "docker stop myapp || true && docker rm myapp || true"
    - ssh user@prod-server "docker run -d --name myapp -p 5000:5000 $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual # Кнопка для ручного запуска
```

## Часть 4. 10 вопросов с собеседований

### Вопрос 1. В чем разница CI, Continuous Delivery и Continuous Deployment?
**Ответ:**
*   **CI (Интеграция):** Код часто сливается в общую ветку, автоматически собирается и тестируется.
*   **CD (Доставка):** Код автоматически готов к деплою, но выкатка на прод происходит **вручную** (кнопкой).
*   **CD (Развертывание):** Код автоматически деплоится на прод **без участия человека**, если тесты прошли.

### Вопрос 2. Как бы ты построил идеальный пайплайн?
**Ответ:**
1. **Триггер:** Пайплайн запускается на каждый `git push` или Pull Request.
2. **Стадия Build:** Сборка Docker-образа с кэшированием слоев.
3. **Стадия Test:** Параллельный запуск линтеров, юнит-тестов и сканеров безопасности (например, Trivy на уязвимости).
4. **Стадия Staging:** Автоматический деплой на тестовый сервер.
5. **Стадия Production:** Деплой только после ручного подтверждения (Continuous Delivery), либо автоматически (Continuous Deployment). Обязательно с возможностью быстрого отката (rollback).

### Вопрос 3. Чем отличаются `artifacts` и `cache`?
**Ответ:**
`artifacts` передаются между задачами (например, бинарник из build в deploy) и хранятся после завершения пайплайна. `cache` используется для ускорения повторных сборок (например, `node_modules`) и не гарантирует передачу между задачами, если не настроен `needs`.

### Вопрос 4. Что такое `needs` и зачем он нужен?
**Ответ:**
Это способ нарушить порядок этапов и запустить задачу раньше, как только готовы её прямые зависимости. Это сильно ускоряет пайплайн (DAG).

### Вопрос 5. Как вы обрабатываете секреты (пароли, ключи) в пайплайне?
**Ответ:**
Никогда не хардкодить в `.gitlab-ci.yml`. Использовать **CI/CD Variables** в настройках GitLab. Важно помечать их как **Masked** (скрытые в логах) и **Protected** (доступные только в защищенных ветках, например `main`).

### Вопрос 6. Что такое `extends` / `include` в GitLab CI?
**Ответ:**
Это способы переиспользования кода в `.gitlab-ci.yml`.
*   **`extends`** позволяет наследовать настройки от другой задачи (чтобы не дублировать `script`).
*   **`include`** позволяет подключать внешние файлы `.yml` (например, общие шаблоны для всех проектов компании).

### Вопрос 7. Что такое `only` / `except` (или `rules`)?
**Ответ:**
Это условия, при которых задача запускается или нет. `only` — запускать только для указанных веток/тегов. `except` — запускать для всех, кроме указанных. В новых версиях GitLab рекомендуется использовать `rules`, так как он более гибкий (можно комбинировать условия `if`, `changes`, `exists`).

### Вопрос 8. Что такое Docker-in-Docker (dind) и зачем он нужен?
**Ответ:**
Это запуск Docker-демона внутри контейнера. Нужен для того, чтобы внутри CI-пайплайна можно было собирать Docker-образы. В GitLab CI для этого используется сервис `docker:24.0-dind` и переменная `DOCKER_HOST=tcp://docker:2375`.

### Вопрос 9. Что такое GitOps?
**Ответ:**
Это подход, при котором **Git является единственным источником правды** для инфраструктуры. Все изменения (конфиги Kubernetes, Terraform) хранятся в Git. Специальный агент (например, ArgoCD или Flux) следит за репозиторием и автоматически применяет изменения в кластер.

### Вопрос 10. Как откатить деплой (rollback), если новая версия сломалась?
**Ответ:**
В GitLab CI можно использовать `environment` с указанием `on_stop` (задача для отката). Либо вручную перезапустить предыдущий успешный пайплайн. В Kubernetes для этого используется `kubectl rollout undo`.
